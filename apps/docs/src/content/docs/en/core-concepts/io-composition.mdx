:::caution
Current releases do not support embedding `io()` nodes directly inside another `io()`.
For example, `io({ akey: io(0) })` is treated as a plain object and fails during clone/snapshot.
:::

## Goals

- Allow existing `IoUnit` / `IoScope` / `IoArray` nodes to be reused inside a Tree.
- Preserve identity: `b.akey === a`.
- Bubble updates and subscriptions through the parent Tree with path prefixes.
- Snapshots should read from the referenced node.

## Proposal Summary

- While building a Tree, `io()` detects IO nodes and mounts them as reference nodes.
- Reference nodes are not deep-cloned or expanded; they only participate in bubbling and path mapping.
- `set` / `commit` against a reference node writes through to the referenced node.
- Reference nodes can come from other Trees or standalone Units.

## Implementation Notes (Draft)

- In `core/node-factory.ts`, `createTreeNode` should detect IO nodes first (`getInternal()?.kind`) and avoid treating them as plain objects.
- Call `registerSubtree` and `setPathNode` for referenced nodes to keep devtools and path lookups working.
- Type-level inference (`utils/types.ts`) should treat `IoUnit` / `IoScope` / `IoArray` as leaves to avoid re-expansion.
- `utils/updates.ts` and `extensions/relocate.ts` can keep using the existing `getInternal()` dispatch logic.

## Constraints (Initial)

- Disallow cycles (for example, linking a parent node back into its child subtree).
- Define consistent patch path behavior when the same reference node appears in arrays.
- The referenced node’s lifecycle remains owned by the creator.

## Open Questions

- Should we require an explicit API (for example, `link(a)`) to avoid accidental embedding.
- How to visualize multi-parent references in devtools.
